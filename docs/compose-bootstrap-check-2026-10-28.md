# Полный запуск с нуля — 28 октября 2026

Проверен запуск одной командой из корня проекта:

```sh
docker compose up --build
```

После появления веб-сервера открыть http://localhost:8080. Устанавливать Ollama, Python, Go, создавать `.env`, вводить LLM API-ключ или скачивать модель вручную не требуется. Docker сам собирает приложение, скачивает закреплённые веса Qwen3-4B-Instruct-2507 Q4_K_M (2 497 281 120 байт), проверяет SHA-256 и запускает llama.cpp. Нужны Docker с Compose, интернет и достаточные ресурсы; первый запуск зависит от скорости сети и CPU.

Этот отчёт заменяет промежуточные результаты [27 октября](compose-bootstrap-check-2026-10-27.md). Финальный runtime использует 4B; упоминания прежней 9B в историческом отчёте не относятся к текущему default.

## Условия и результат

Использована отдельная копия исходников без `.env` и `.runtime`, новый Compose project с отсутствующими volumes и новый пустой BuildKit builder. Команда выполнялась с пустым env-файлом, без внешнего LLM и API-ключа. Воспроизводимый harness: `scripts/check-cold-start.py`; конфигурация ограничений: `docs/validation/docker-cpu-2026-10-27/resource-limits.yml`.

Реальное исполнение: Linux ARM64 в Docker на MacBook Air M4 / 32 GiB. Docker VM: 10 vCPU / 7,75 GiB; все три тестовых сервиса совместно ограничены четырьмя CPU (`cpuset=0-3`). Лимиты памяти: модель 5 GiB, агент 512 MiB, приложение 256 MiB; container swap отключён. Модель не была убита по OOM: `oom=0`, `oom_kill=0`, `OOMKilled=false`. Часть лимита занимает файловый кэш весов; это не только память inference. Конкурирующие модельные проверки были остановлены.

| Этап от начала команды | Первый запуск | Повторный запуск |
|---|---:|---:|
| Страница с прогрессом доступна | 44,904 с | 2,080 с |
| Модель healthy | 153,505 с | 11,272 с |
| Приложение `/ready` | **229,694 с** | **92,136 с** |
| Все три контейнера healthy | 235,861 с | 93,311 с |

Первый замер включает первоначальный запуск BuildKit (9,7 с), сборку образов без кэша, скачивание весов и прогрев. Загрузка с проверкой SHA-256 заняла 96,509 с; загрузка в память — 3,210 с; начальный prefill — 82,108 с. Повторный запуск также выполнялся через `up --build`: проверенные веса взяты из volume за 0,001 с, повторного скачивания не было. Прогрев после остановки процесса остаётся необходимым.

## Поведение для организатора

- В браузере и Docker logs видны этапы скачивания, загрузки в память и прогрева. При скачивании показываются реальные байты, процент, скорость и прошедшее время. Для прогрева не придумывается процент.
- Страница автоматически переходит в приложение после готовности модели и агента. До этого API изменения поездок возвращает 503, `/health` отражает работоспособность процесса, `/ready` — фактическую готовность.
- Прерванное скачивание продолжается через HTTP Range; неполный или повреждённый файл не запускается. После исчерпания повторных попыток видна ошибка.
- Стартовый prefill имеет отдельный бюджет 300 с и не обрывается пользовательским таймаутом 90 с. Быстрое переподключение gRPC устраняет лишнее ожидание после готовности агента.

## Проверка пользовательского сценария

Настоящий браузер наблюдал 46 различных растущих значений скачанных байтов, этапы загрузки и прогрева и автоматический вход в приложение. Проверены desktop и мобильный экран 390 px, без горизонтального переполнения и ошибок JavaScript. Моки модели в этой проверке не использовались.

На свежем экземпляре без API-ключа пройден полный сценарий: ввод поездки, уточнение, выбор и изменение отелей и транспорта, ограничения пересадок, свои билеты, оформление, перезагрузка и PDF. Сохранено 33 200 ₽, PDF сформирован за 1,692 с. После остановки и повторного запуска оформленная поездка сохранилась. Новый запрос из чистой браузерной сессии вызвал настоящую модель и вернул корректное уточнение за 15,036 с; ошибок браузера нет.

Дополнительные проверки: 9 bootstrap-тестов модели (включая реальный HTTP обрыв и докачку), 3 bootstrap-теста агента, Go race/vet и 211 Python unit tests прошли. Итоговый набор качества CPU: 95/95, медиана 3,62 с, p95 8,52 с, максимум 33,62 с. Подробности и методика — в [CPU-отчёте](validation/docker-cpu-2026-10-27/README.md).
