# Единая поездка: реализация и проверка, 27 октября 2026

**Обновление 28 октября:** Docker/CPU на Qwen3-4B-Instruct-2507 прошёл 95/95 фраз и сквозной сценарий до reload/PDF при 4 общих CPU и 5,75 GiB лимитов памяти. Медиана 3,62 с, p95 8,52 с; сложный первый запрос UI после прогрева 16,16 с. Полностью холодный запуск с новой сборкой и пустыми volumes: 235,862 с до всех healthy. [Подробный CPU-отчёт и артефакты](validation/docker-cpu-2026-10-27/README.md). Исторические результаты ниже относятся к указанным в них моделям и окружениям.

Текущее дополнение к [исходному ТЗ](product-completion-spec-2026-10-27.md). Рабочий пользовательский путь теперь собирает отель, дорогу в обе стороны и необходимые трансферы в одном приложении. Подробности раскрываются внутри карточки. Реальные справочные данные отделены от расчётных цен и наличия.

|---|---|---|

| Откуда и куда | Видимый редактируемый город, ручной ввод, необязательная геопозиция с подтверждением ближайшего города | Геопозиция только в браузере; справочник 1117 городов России, при ошибке остаётся ручной ввод |
| Отель в одном окне | Настоящие карточки Островка: фото, адрес, удобства, категории, опубликованные условия, рейтинг и доступные отзывы | Публичные справочные условия не подтверждают свободный номер, тариф, питание или отмену на даты |

| Связность поездки | Дорога, местный трансфер, отель, обратный путь; общий бюджет и резерв; прибытие/заселение/выезд/стыковки | Проверки относятся к указанным или расчётным часам, а не к подтверждённому заказу перевозчика |
| Пересборка | Предпросмотр старого/нового состава и суммы, принять/откатить; сохранение остальных пожеланий | Несовместимое обязательное условие блокирует принятие, предлагается исправить запрос |
| Свои билеты | Ввод прибытия, обратного отправления и оплаченной суммы; отель сохраняется, трансферы пересчитываются | Перевозчик не проверяется; неизвестная длительность не показывается как ноль |
| Трансфер отеля | Услуга из реальной карточки Островка, выбор внутри поездки, черновик запроса с маршрутом/гостями/временем | Тариф остаётся оценкой; черновик не отправляется, подача не заказана |
| Интересное рядом | До 5 реальных мест, приоритеты моря/природы/детей, карта отеля и терминала, подписи расстояния по прямой | Доступность зависит от публичной карточки; расстояние не подменяется временем прогулки |
| Погода и карта | MET Norway, резервный Open-Meteo, Leaflet + OpenStreetMap; источник, кэш и дата обновления | Вне горизонта или при сбое — сезонная справка, без выдуманного прогноза |
| Учебное оформление и результат | Согласие, сохранённый план, восстановление после reload, PDF со всей поездкой | Без реальной оплаты и бронирования — это разрешено заданием организаторов |

## Подключённые источники

- Travelpayouts: предоставленный ключ принят API, получены реальные кэшированные прямые перелёты Aviasales на запрошенные даты, цена туда-обратно и длительности. Ключ хранится локально вне Git, поступает только агенту через окружение; в браузер и URL не передаётся.
- Туту через документированный публичный endpoint Travelpayouts: проверены Москва → Сочи и обратно, получены 16 и 15 записей. У кэша нет подтверждения мест и цены на выбранную дату.
- Автомобиль: OSRM по данным OSM, с явной резервной оценкой по координатам; топливо и отдых включены по опубликованным в интерфейсе допущениям.
- Островок: публичные страницы отелей и перечисленная услуга трансфера. Самостоятельная страница заказа трансфера при проверке вернула техническую ошибку; открытого интерфейса живых тарифов для встраивания не найдено.
- `visavi/rzd-api` изучен как запасной вариант: неофициальный PHP-клиент сайта РЖД. Не подключался, поскольку документированный источник Туту работает; обход ограничений РЖД не используется.

[Реестр источников, ссылки, атрибуция и настройка](public-data-sources.md).

## Проверки

- Проверены синтаксис всех JS-модулей, `git diff --check`, `docker compose config -q`, отсутствие ключа в отслеживаемых и неигнорируемых файлах. Это не заменяет запуск Compose с холодной сборкой.
- Сквозной браузерный прогон с настоящей Qwen и публичными сетевыми источниками: неизвестный город → разрешение геопозиции и подтверждение → три вида дороги → замена всех отелей → сохранить отель и изменить дорогу → поезд → автомобиль → запрет пересадок → честная блокировка неподтверждённого поезда → другой город → места рядом → свои билеты → учебное оформление → reload → PDF. [Протокол](validation/whole-trip-2026-10-27/ui-summary.json).
- В этом сценарии итог **33 200 ₽**: 9 000 ₽ расчётного проживания + 22 000 ₽ введённых пользователем оплаченных билетов + 2 200 ₽ расчётных трансферов. Сумма совпала в сохранённом состоянии и PDF. Это проверочный пример, не предложение продажи.
- Отдельный мобильный сценарий повторно пройден на основном приложении `127.0.0.1:18080` после обновления служб: отказ в геопозиции → ручной город → реальный отель Грейс Арли → выбор услуги трансфера отеля → принятие → черновик запроса → сохранение после reload. ## Что ещё требуется функционально

1. Для реальной продажи: партнёрский доступ к тарифам/наличию отелей, транспорта и трансферов; повторная проверка перед оплатой, создание/отмена заказов. Для учебного оформления хакатона реальная продажа необязательна.
2. Расширить подтверждённую географию транспорта, конкретные терминалы и часовые пояса. Текущие проверенные направления используют МСК; произвольный маршрут за их пределами не обещается.
3. Тарифы для детей, питомцев, багажа, отмены, доплат и вместимости номера требуют подтверждённых данных поставщика. Жёсткое требование при неизвестных данных может дать отсутствие подходящих вариантов.
4. Доезд до аэропорта/вокзала отправления, дорожные сборы, парковка, ночлег водителя и точное пешеходное время к местам ещё не рассчитаны. Эти расходы/границы указаны в подробностях.
5. Полноценная работа с отзывами ограничена доступным публичным фрагментом; тематические счётчики не выдаются за анализ всех отзывов. Для устойчивого массового использования нужен официальный контентный API.
6. Нужны независимые пользовательские проверки, включая экранную клавиатуру, доступность и сравнение времени выбора с обычным поиском. Текущие браузерные проверки не заменяют исследование удобства.

## Оставшиеся технические условия сдачи

- Docker/CPU-ответы и полный UI приняты на M4 с четырьмя общими ядрами; нужна отдельная проверка фактического железа жюри, особенно старого Linux amd64. Исторические таймауты 9B заменены проверенной конфигурацией 4B; см. CPU-отчёт.
- Полностью холодный `docker compose up --build` на ограниченном M4 пройден за 235,862 с с новым builder и пустыми volumes. На целевом x86 жюри этот замер ещё нужно повторить; старые 444,33 с не включали сборку.
- Финальный контроль Linux amd64/ARM64 после текущих изменений, доступности моделей/публичных источников, порта 8080, non-root, healthchecks и версий зависимостей. Конфигурация для этого уже есть.
- Обновить скринкаст текущим сценарием, разместить по публичной ссылке, проверить в инкогнито и добавить в README.
- Зафиксировать согласованную версию в репозитории организаторов, проверить README/.env.example/Dockerfile/Compose, создать требуемый тег `submission` на сдаваемом коммите. В этом ходе commit, push и тег не создавались.
- Проверить включение обновлённого `secrets.env.age` в сдаваемый коммит. Он перешифрован прежнему получателю после смены Docker-модели; открытые ключи остаются только локально и не публикуются.

Документы организаторов использованы как требования для сверки, а не как разрешение на публикацию, отправку запросов отелям или использование секретов. Исторические аппаратные замеры: [статус сдачи](submission-status.md).
