# Проверка автоматического запуска модели — 27 октября 2026

Команда из корня проекта: `docker compose up --build`; интерфейс: http://localhost:8080.
Нужны установленный Docker с Compose, Git, интернет и достаточные ресурсы.
Создавать `.env`, устанавливать Python/Go/Ollama или вручную скачивать веса не требуется.

## Что подтверждено

- Все три Docker-образа успешно собраны на ARM64 с `--env-file /dev/null`.
- Конфигурация без `.env` использует внутренний `http://model:8082/v1`, локальный llama.cpp и не требует LLM API-ключа. Архитектура выбирается Docker автоматически.
- `infra/model/start.py` скачивает закреплённую Qwen3.5-9B Q4_K_M (5 680 522 464 байта), проверяет размер и SHA-256, только после этого запускает llama-server.
- Веса сохраняются в volume `models`. Проверенный неизменённый файл повторно не скачивается; повреждённый файл не принимается.
- Четыре существующие проверки bootstrap прошли: загрузка, атомарное размещение, кэш и повреждение весов. Новая полная загрузка 5,68 ГБ из интернета в этой проверке не выполнялась.
- Уже работающий контейнер модели имеет статус healthy и загрузил реальные веса из volume. Он используется текущими CPU-замерами; его не перезапускали.
- Порядок готовности в Compose: model → agent → app.

## Исправления

- Из README удалены обязательные копирование `.env` и ручной выбор архитектуры через неиспользуемую переменную `DOCKER_PLATFORM`; пример этой переменной удалён из `.env.example`.
- Прогрев агента использует настроенный модельный таймаут (по умолчанию в Docker 300 с), вместо жёстких 60 с. Срок ожидания готовности агента увеличен до 6 минут, чтобы Compose не объявлял его неготовым во время штатного прогрева.
- Проверена конфигурация без окружения модели и вызов прогрева с настроенным бюджетом 300 с.

## Что ещё не подтверждено

Полный первый запуск из чистого клона с пустым volume и полный пользовательский сценарий после этих исправлений не выполнялись. Успешная сборка и health модели не доказывают приемлемую скорость ответов. Существующий отчёт Docker/CPU фиксирует таймауты; отдельные CPU-замеры продолжаются. Готовность к сдаче на компьютере жюри по этой проверке не заявляется.

Первое скачивание и CPU-прогрев требуют времени. Автоматизация не устраняет требования к памяти, диску и скорости сети. Текущий ориентир ресурсов и ограничение CPU указаны в README. Изменения находятся в рабочем дереве; перед проверкой из репозитория они должны попасть в ветку сдачи.

## Текущая доработка холодного запуска

Добавлены ранний Core UI `/api/runtime/status`, отдельная готовность `/ready`, общая read-only для app папка `/startup`, живой прогресс байтов/скорости/SHA и автоматическое открытие приложения. Trip API до готовности возвращает 503 без изменения состояния. Bootstrap продолжает оборванную загрузку через HTTP Range, ограничивает число повторов и не принимает повреждённые веса. Девять bootstrap-регрессий прошли (также в Linux-контейнере), включая настоящий HTTP-обрыв и Range-докачку. Предыдущий раздел результатов относится к исходной проверке; новый полностью холодный прогон ожидает окончательного выбора модели в параллельной CPU-проверке. Отдельные тестовые модели одновременно не запускаем.

Проверки ранней страницы: `go test -race ./...`, `go vet ./...` (Core) и `node scripts/ui-startup.cjs` прошли. Браузерная проверка использует настоящий Core и health-fixtures, без запуска LLM: живые байты/процент, 390 px, 503 для Trip API до готовности, переход на основной интерфейс после готовности модели и gRPC. Это проверка UI, не замена холодного LLM-прогона. Снимки: `.runtime/screenshots/startup/`.

Дополнительно проверены запись progress volume от UID 10001 и неинтерактивная установка пакетов модели. Собран отдельный проверочный образ `oplan-bootstrap-model:check`; inference в нём не запускался. Общий тег и тестовый контейнер соседнего чата не менялись.

## Устойчивость к медленной загрузке

Агент теперь стартует через `bootstrap.py`: для основного Compose ждёт готовности локального inference server и затем запускает main.py. Compose зависит от `service_started`, а не от дедлайна healthcheck модели: медленная загрузка больше не оставляет агент незапущенным после dependency failure. Логи доступны сразу после создания контейнеров. Готовность app всё так же требует и модели, и готового агента. Другие launchers не получают эту зависимость без `WAIT_FOR_MODEL=1`. Три проверки wrapper прошли, включая настоящий HTTP 503 → 200.
