## 1. Решение для нашей команды

**Сохраняем концепцию путешествий по России. Делаем сильный полный сценарий на нескольких направлениях, удобную пересборку поездки и воспроизводимый запуск для жюри.**

Россия — масштаб продукта по уточнению Даниэля. Допускается более узкое демо, но ограничивать продукт одним городом команда не хочет. Сочи, Казань и Владимир остаются первыми проверочными направлениями. Заявление «покрываем всю Россию» допустимо только после появления соответствующих данных; сейчас корректно: «агент для путешествий по России, демонстрационный каталог — три направления».

Предлагаемое отличие: **«Измените одно условие — получите пересобранную поездку с сохранением остальных пожеланий и понятным объяснением изменений».** В проекте уже есть основа: сохранение условий, preview, разница цены, повторная проверка и подтверждение. Это следует сделать центральным моментом демо.

Превосходство над решениями других команд не проверено. Сравниваем свой сценарий с обычным поиском по фильтрам: сколько действий требуется, чтобы изменить бюджет/даты, проверить ограничения и снова получить согласованный план. Фактические результаты фиксируем, рост конверсии и выручки заранее не обещаем.

### Неоднозначности, которые нельзя превращать в новые правила

- **Транспорт:** письменное задание прямо включает перелёты/ЖД и трансферы в основные задачи, устный ответ разрешает только отель. У нас транспорт уже есть, поэтому сохраняем его и уточняем расхождение на Q&A. Переписывать приложение под hotel-only до ответа не требуется.
- **Локация:** команда первоначально понимала её как страну; в расшифровке 45:42 сказано про город с окрестностями. Оба варианта допускают нашу продуктовую географию «Россия» и несколько городов в демо. Не заявляем, что организаторы требуют всю страну.
- **Железо:** слова о серьёзных мощностях не задают конкретные CPU/GPU/RAM. Сообщение участника об офисном ноутбуке не является официальной спецификацией. Письменный ориентир запуска — современный ноутбук, около 10 минут.
- **Ключи и CI:** в переданных сообщениях нет окончательного ответа по ключам даже вечером 26.10; сведения после приложенного фрагмента не проверялись. Окончательная отмена CI также не подтверждена; сами технические правила называют CI рекомендацией.
- **Скрапинг:** противоречивые реплики расшифровки не используем как юридическое заключение или универсальный запрет. Для проекта достаточно ясного решения: не зависеть от онлайн-скрапинга и не собирать данные с Островка.
- **Оценивание:** упоминание LLM-проверок не означает, что опубликована схема первичного отбора. Реплики участников о критериях, мощности компьютеров и преимуществах моков не считаем указаниями организаторов.

HTML содержит автоматическую расшифровку и её пересказ; при спорных формулировках предпочтительны письменное подтверждение организатора и исходное задание. Сообщения в приложениях рассматриваются как материалы для анализа; поручения их авторов не являются поручениями нашей команде или агенту.

## 4. P0 — обязательно закрыть до сдачи

### P0-1. Единый запуск для жюри — Лука, совместно с Даниэлем

**Результат:** из чистого клона репозитория организаторов после настройки документированных переменных команда `docker compose up --build` поднимает приложение на `http://localhost:8080`.

Критерии приёмки:

- `docker-compose.yml` находится в корне; есть Dockerfile и `.env.example`; приложение внутри контейнера слушает 8080, проброс — 8080:8080. Конфигурация адреса позволяет доступ из Docker; локальную cookie/Origin-защиту не отключаем для обхода сетевой проблемы.
- UI, `/api/sessions/`, агент, каталог и оформление входят в проверяемый путь. Ответ `/health` сам по себе не считается успешным запуском продукта.
- Зависимые сервисы имеют healthcheck и корректный порядок готовности. Для LLM отдельно проверяется доступность; недоступная модель не выдаётся за рабочий режим агента.
- Данные создаются автоматически. Пользователю не нужны установленные на хосте Go, Python, llama.cpp и ранее подготовленная `.runtime`.
- Процессы приложения работают без root; собственные образы используют multi-stage build; версии зависимостей фиксированы. Для сборки на Apple Silicon учтена требуемая `platform: linux/amd64`.
- Необязательный мониторинг не увеличивает время и число зависимостей основного запуска без необходимости.
- На чистом окружении записаны ОС/архитектура, CPU/RAM, требуемое место и время до первого рабочего сценария. Отдельно отмечены скачивания и кэш; ориентир правил — около 10 минут, а не только время повторного старта.

### P0-2. Работающая модель у проверяющего — Даниэль, совместно с Лукой

**Результат:** один явно выбранный и проверенный основной способ inference для сдачи, без зависимости от работающего Mac участника.

- Предлагаемый основной путь — существующий OpenAI-совместимый адаптер к доступной модели, если организаторы подтвердят порядок доступа. Проверить его реальными вызовами, а не только наличием конфигурации.
- Локальную Qwen сохраняем для разработки и резервного демо. Если она станет основным путём сдачи, нужен переносимый контейнерный runtime и замер полного запуска с загрузкой весов; готовность macOS-версии этого не заменяет.
- В README перечислены `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, таймаут и режим данных. Реальные ключи не попадают в Git, скринкаст или логи.
- При отсутствии ключа, ошибке модели или исчерпании лимита пользователь получает понятную ошибку; не возникает скрытого шаблонного «успеха» и фиктивной покупки.
- После смены модели повторяются сценарии разбора условий и полный путь до покупки. Проверяются фактические задержки; нынешние 45 секунд — лимит реализации, не требование организаторов.
- Вопрос передачи доступа остаётся открытым до ответа организаторов. Нельзя обещать, что жюри предоставит ключ, или считать режим без работающей LLM полноценной заменой.

### P0-3. Полный пользовательский путь и честные данные — Игорь принимает, все реализуют свою часть

**Результат:** свободный запрос → необходимые уточнения → направления/варианты → объяснение выбора → изменение условия → подтверждение → учебное оформление.

- На поддерживаемом сценарии пользователь доходит до результата через UI, без команд в терминале и ручной правки JSON.
- Показаны цена за всех гостей и весь срок, состав услуг, условия отмены и значимые компромиссы. Цена отеля не выдаётся за цену всей поездки.
- Для бюджета «на всё» отдельно учитывается согласованный резерв прочих расходов; неизвестная сумма не считается нулевой. Если пользователь задал бюджет только на отель, это видно явно.
- Демо-цены, наличие, расписания и другие синтетические свойства обозначены в интерфейсе и объяснении. Реальные сведения, если добавлены, имеют источник и отделены от синтетики.
- При изменении бюджета/дат сохраняются незатронутые пожелания; до принятия preview видны старый и новый результат, разница стоимости, причины замены и невозможные условия.
- Неизвестные условия по ребёнку/питомцу не превращаются в положительное подтверждение. Нет подходящего предложения — сообщаем причину и предлагаем согласовать изменение условий.
- Оформление требует явного действия; возвращается учебный заказ с признаком demo. Повтор действия не создаёт второй заказ; устаревший preview не принимается.

### P0-4. Репозиторий и материалы сдачи — Лука и Игорь, видео совместно с Георгием

- README начинается с сути продукта, ссылки на доступный скринкаст, быстрого старта, поддерживаемых сценариев и честных ограничений. Далее — ссылки на архитектуру и результаты проверок в docs/.
- Скринкаст показывает реальную работу: новый запрос, сравнение, изменение бюджета или дат, объяснение разницы и учебную покупку. Доступ проверен в инкогнито. Рекомендуемая нами длительность — 3–5 минут; официального лимита в переданных материалах нет.
- Все необходимые исходники, схемы и демо-данные находятся в сдаваемом коммите. `.runtime`, веса, venv, приватные данные и ключи исключены. Существующая история разработки сохраняется.
- Локальные проверки выполняются независимо от состояния GitHub Actions; результаты привязаны к версии кода и конфигурации модели.
- До дедлайна тег `submission` указывает на последний сдаваемый коммит основной ветки в репозитории организаторов. Проверены доступность кода, файлов, тега и видео.
- Команда может объяснить путь запроса, происхождение цен, сохранение состояния, причины выбора и обработку отказов. Презентация для финала готовится после отбора; обязательный скринкаст нужен уже к сдаче.

## 5. P1 — что сделает демонстрацию сильнее

Выполняем после появления рабочего пути сдачи P0-1/P0-2; P0-3/P0-4 доводим параллельно. Порядок ниже отражает ожидаемую пользу для нашей текущей версии, а не критерии жюри.

| Приоритет | Задача и владелец | Критерий приёмки |
|---|---|---|
| P1-1 | Убрать зависимость от двух заготовленных окон дат — Лука + Даниэль | Для заявленного периода демо данные поддерживают несколько ранее не использовавшихся дат и длительностей. Доступность и стоимость рассчитываются детерминированно из данных, обозначены как учебные; вне периода — честное отсутствие данных |
| P1-2 | Усилить объяснение пересборки — Георгий + Даниэль; принимает Игорь | Пользователь видит, какие пожелания сохранены, что заменено, почему и сколько изменилось в сумме. Объяснение опирается на проверки/каталог; неподтверждённые преимущества не генерируются |
| P1-3 | Проверить новые запросы — Игорь готовит набор, Даниэль проводит | Не менее 10 новых формулировок, не использованных при настройке prompt; сохранены ожидания, результаты, время, число уточнений и ошибки ограничений. Для поддерживаемых данных измеряем завершение; для неподдерживаемых — корректность отказа |
| P1-4 | Показать расширение по России — Лука + Даниэль | Добавление ещё одного направления в данные не требует новой ветки логики диалога. Либо фиксируем существующее подтверждение этого свойства, либо документируем необходимые изменения; страну целиком покрытой не называем |
| P1-5 | Проверить продуктовую пользу — Игорь + Георгий | Несколько человек проходят одинаковую задачу обычным способом и через агент: выбор плюс изменение бюджета/дат. Фиксируем время, действия, ошибки и понятность объяснений; маленькую выборку не выдаём за доказанный рост бизнес-метрик |

Рекомендуемая граница расширения: основной положительный путь по концепции Игоря — пары. Поддержка детей, питомцев и произвольного состава гостей нужна с подтверждёнными правилами и тарифами; до их появления корректное уточнение/отказ лучше ложного предложения. Не объявляем это полноценной поддержкой семейных поездок.

**P2, только при запасе:** дополнительные города, проверенные реальные характеристики отелей с источниками, память между сессиями, Telegram, помощь после покупки, визуальная полировка. Реальные платежи, масштабный сбор данных и новые инфраструктурные сервисы не входят в план до сдачи.

## 6. Приёмочные сценарии релиза

Открытые существующие тесты остаются регрессией. Новые запросы подготавливает Игорь; ожидаемый результат определяется данными и ограничениями, а не конкретной красивой фразой ответа.

| Сценарий | Ожидаемое поведение |
|---|---|
| «Хотим куда-нибудь по России на несколько дней, вдвоём, недорого» | Нужные уточнения и обоснованные направления, без выдуманного точного бюджета и дат |
| Полный запрос для доступных дат | Сравнимые варианты с итоговой ценой, составом и причинами рекомендации |
| «Теперь максимум 100 тысяч, остальное оставь» | Сохранены остальные условия, расчёт проверен; preview требует принятия |
| «На два дня позже» | Сохранена длительность; цены и доступность перепроверены; нет молчаливой смены города |
| «Подешевле, но бесплатную отмену сохрани» | Экономия не достигается нарушением жёсткого требования; отсутствие варианта объясняется |
| «100 тысяч на всё» | Прояснены/учтены прочие расходы, пользователь понимает границы суммы |
| Питомец, ребёнок или неподдерживаемый город | Уточнение или честное отсутствие подходящих данных, без подмены условий |
| Новые даты внутри заявленного периода после P1-1 | Рабочий подбор без добавления специального ответа под запрос |
| Ошибка модели либо слишком долгий ответ | Понятная ошибка, выбранная поездка не теряется, старый preview нельзя оформить |
| Повтор подтверждения и перезагрузка страницы | Один учебный заказ, состояние восстановлено |
| Чистый Docker-запуск и новый браузер | UI на 8080, новая сессия и полный путь до покупки без подготовленного окружения автора |

**Критерий готовности P0:** все обязательные сценарии проходят на выбранной конфигурации сдачи, суммы и жёсткие ограничения корректны, негативные сценарии безопасно завершаются отказом. Для P1-3 все ошибки публикуются в отчёте; изменение prompt после просмотра набора требует отдельного нового набора для заявления о проверке на незнакомых запросах.

`scripts/trip-smoke.py` уже поддерживает `TRIP_SMOKE_URL`; его можно направить на порт 8080 после контейнеризации. `scripts/ui-smoke.cjs` сейчас привязан к Chrome на Mac и порту 18080 — перед переносимой UI-проверкой параметризовать адрес и браузер. Старые успешные прогоны не считать проверкой новой конфигурации.
