# Проверка Linux AMD64 — 28 октября 2026

Все три образа (`app`, `agent`, `model`) собраны и исполнены как `linux/amd64`. Проверка проведена через эмуляцию Docker Desktop на Apple Silicon, а не на физическом Intel/AMD. Она подтверждает совместимость проверенных образов с x86-64, но не скорость на компьютере жюри и не успешный холодный запуск с настройками по умолчанию.

## Результаты

- Запуск без `.env`, LLM API-ключа и внешнего inference. Первый прогон использовал отдельные пустые volumes; веса 2,50 ГБ скачаны и проверены. Сборка образов выполнена отдельно до измерения запуска.
- `uname -m` внутри модели: `x86_64`; llama.cpp build 11853 исполняется. Все три процесса работают с UID 10001.
- Штатный прогрев с лимитом 300 с завершился `model_timeout`: эмуляция обрабатывала промпт примерно по 3 токена/с. Агент перезапустился. Этот прогон не считается успешным.
- Для отдельного прогона заданы `MODEL_WARMUP_TIMEOUT_SECONDS=900` и `AGENT_TURN_TIMEOUT_SECONDS=300`. Все три контейнера стали healthy, `/ready` вернул 200. От начала повторного прогона до готовности — 258 с, до всех healthy — 262 с. Использовались уже загруженные веса и частично обработанный контекст модели; это **не** время холодного запуска.
- В настоящем браузере пройден путь: запрос → три варианта отеля → оформление → учебная покупка → перезагрузка с восстановлением заказа → PDF (704 146 байт). Первый ответ — 68,471 с, включая 55,206 с модели и 12,589 с источников. Моки модели не использовались.
- Ошибок JavaScript нет; `OOMKilled=false` у всех трёх контейнеров.

Основные defaults проекта не изменены ради прохождения эмуляции. На Intel/AMD Docker выбирает AMD64 нативно. Не следует принудительно включать AMD64 на Apple Silicon для обычной работы: это значительно замедляет модель. Для подтверждения ориентира установки ≤10 минут на Intel/AMD нужен отдельный прогон на физическом x86-64.

## Воспроизведение

Из корня репозитория; порт 18084 должен быть свободен. Проверка занимает до 5 GiB памяти модели дополнительно к другим запущенным моделям. Не запускайте одновременно несколько стеков при недостатке RAM.

```sh
docker compose --env-file /dev/null -p oplan-amd64-check -f docker-compose.yml -f docs/validation/amd64-2026-10-28/compose.yml build
docker compose --env-file /dev/null -p oplan-amd64-check -f docker-compose.yml -f docs/validation/amd64-2026-10-28/compose.yml -f docs/validation/amd64-2026-10-28/extended-timeouts.yml up -d
# Открыть http://localhost:18084 и дождаться подготовки.
docker compose --env-file /dev/null -p oplan-amd64-check -f docker-compose.yml -f docs/validation/amd64-2026-10-28/compose.yml -f docs/validation/amd64-2026-10-28/extended-timeouts.yml ps
```

Для воспроизведения неуспешного штатного прогона исключите `extended-timeouts.yml`. Повторение на том же проекте использует сохранённые веса. Файл override использует `!override` для порта; проверенная версия Compose — 5.1.2.

[Результат запуска и идентификаторы образов](result.json), [результат браузерного сценария](browser-result.json), [сценарий проверки](browser-check.cjs). Для браузерной проверки нужны локальные Node.js, Chrome и Playwright из `.runtime/browser/node_modules`; они не нужны для запуска приложения. Команда: `node docs/validation/amd64-2026-10-28/browser-check.cjs` из корня проекта.

Исходная ветка на момент начала проверки — коммит, указанный в `result.json`. Во время проверки в рабочей папке параллельно менялся код приложения; данный отчёт относится к образам с указанными ID, а не удостоверяет последующие изменения интерфейса. После проверки тестовые контейнеры остановлены, основной экземпляр возвращён на порт 8080.
