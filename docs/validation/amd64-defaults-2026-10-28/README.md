# Linux AMD64: настройки по умолчанию, 28 октября 2026

**Рабочий HTTP-сценарий прошёл на Linux AMD64 без `.env` и ключей. Время холодного запуска на физическом Intel/AMD пока не подтверждено.** Доступный прогон использовал эмуляцию AMD64 на Apple Silicon; переносить его время на сервер жюри нельзя.

## Холодный запуск опубликованного варианта

Новый клон коммита `1e7331e72b80033d7b0a39b76157849e67ede365`, отдельный builder без build cache и изначально отсутствующие volumes. Нет `.env`, готовых весов, LLM API key и Travelpayouts token. Единственный override — `platform: linux/amd64` для каждого сервиса: [platform.yml](platform.yml). На физическом x86 такой override не нужен. [Подготовка](preparation.json).

```sh
python3 scripts/check-cold-start.py \
  --project oplan-amd64-defaults-20261028 \
  --override /absolute/path/platform.yml \
  --output /absolute/path/startup.json --timeout 2100
```

Создание конфигурации нового builder и клонирование выполнялись до таймера; загрузка и запуск BuildKit, сборка и веса входят в таймер.

Итого **19 мин 32 с в эмуляции**. Скачивание прошло с первой попытки, размер 2 497 281 120 байт и SHA-256 совпали с lock-файлом. Первый прогрев достиг штатного предела 900 с; агент автоматически перезапустился один раз. Повторный прогрев использовал уже вычисленный контекст модели и завершился за 6,648 с. Ручных правок, копирования весов и OOM не было. Это успешный автоматический старт, но **не выполнение цели 600 с в этом окружении**.

## Найденные проблемы и итоговый рабочий сценарий

Первый свободный запрос после старта упёрся в прежний предел ответа 90 с: [реальный неуспешный результат](http-before-timeout-fix.json). В корневом Compose предел для Core и агента увеличен до **300 с**. Это верхняя граница; готовый ответ возвращается сразу. Предел прогрева остаётся 900 с. Зашифрованные настройки также обновлены, чтобы не возвращать старый предел после расшифровки.

`/api/local/status` ранее всегда объявлял синтетический источник. Исправлено соответствие настроенному `JOURNEY_DATA_SOURCE`; публичные карточки сопровождаются явными признаками расчётных цен и учебного бронирования. Изменение покрыто Go-тестом.

После исправлений app и agent пересобраны из текущих исходников в том же изолированном клоне. `.env` и ключей по-прежнему нет; настройки 300/900 применены из Compose. Модель и её кэш сохранены, поэтому **эти последующие проверки не являются повторным холодным замером**. Исходники и совпадение с тестовым checkout: [manifest](final-source-manifest.json); образы, UID 10001, отсутствие OOM/перезапусков и ключей: [final-containers.json](final-containers.json). Dockerfile модели исправлен отдельно ниже; работающий модельный образ в HTTP-прогоне собран до этого исправления, бинарный архив и его SHA-256 не менялись.

В контейнер agent добавлена команда без дополнительных зависимостей:

```sh
docker compose up --build
# Во втором терминале:
docker compose exec -T agent python -m travel_agent.verify_running
```

Команда непосредственно внутри AMD64 agent завершилась с кодом 0: [JSON](http-journey.json), [stderr](http-journey-stderr.txt). До готовности подождала около 12 с после пересоздания агента; первый запрос — 58,094 с, весь проверочный сценарий — 70,265 с. Это отдельная функциональная проверка с уже скачанной и прогретой моделью. Независимый запуск того же HTTP-клиента с хоста также прошёл: [результат](http-journey-host-client.json).

Проверено: HTTP health/readiness; настоящий вызов локальной модели; Москва → Сочи, даты, двое взрослых, бюджет, бассейн и запрет ночных рейсов; три карточки из публичного источника; сумма компонентов и соблюдение бюджета; выбор отеля; изменение дат с обязательным принятием новой цены; учебное оформление; восстановление сохранённого заказа. Реальные бронирование и оплата не выполняются. Браузер/PDF в этом AMD64-прогоне не проверялись; прежняя браузерная проверка относится к [ARM64-прогону](../jury-clean-2026-10-28/README.md).

## Сбой старого сборщика на реальном Linux

Друг команды прислал лог нативного AMD64: `Step 4/16`, выход 1 до `curl` при выборе архитектуры. Причина: старый builder не заполняет автоматический `TARGETARCH` — [документация Docker](https://docs.docker.com/reference/dockerfile/#automatic-platform-args-in-the-global-scope). Исправлено в коммите `10304e31bf43fb74b5d2291ecf6c8fd3dff97dbf`: если аргумент пуст, используется `dpkg --print-architecture` внутри Ubuntu-стадии; неподдерживаемая архитектура выводится в ошибке. Вручную включать BuildKit не требуется.

- Полная download-стадия AMD64 с явно пустым `TARGETARCH` скачала архив x64 и проверила SHA-256: [результат](amd64-empty-targetarch-build.json), [лог](amd64-empty-targetarch-build.log.txt).
- Настоящий legacy builder с `DOCKER_BUILDKIT=0` также успешно выполнил download-стадию без аргумента: [результат](legacy-model-build.json), [лог](legacy-model-build.log.txt). На данном Docker Desktop он выбрал локальный ARM64 base image несмотря на запрошенный `--platform`; этот прогон доказывает legacy-путь на ARM64. Отдельная проверка выше доказывает AMD64-путь с пустым аргументом.

Команде передан коммит для повторного физического замера. Его результат ещё не получен.
